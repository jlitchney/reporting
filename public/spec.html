Campaign Reports — Developer Spec

Internal reference for the AllStar Talent campaign candidate reporting dashboard.

Overview

Campaign Reports is a multi-client reporting dashboard that ingests campaign CSV exports and renders configurable, interactive charts. Each client has their own CSV data, multiple named tabs, and any number of independently configured widgets per tab. All widget configuration (chart type, filters, date range, color, size) is persisted server-side.

Key capabilities:

  • Upload or refresh a CSV for any client at any time
  • Multiple report tabs per client, each independently configured
  • 8 widget types: Total count, Bar chart, Line chart, Column chart, Stacked bar, Pie chart, Table, Funnel
  • Per-widget: accent color, width (¼/½/¾/Full), chart height (S/M/L/XL), per-series colors
  • Drag-and-drop reordering of all widgets
  • Filter by tag, date range (preset or custom), exclude-removed toggle

Architecture

The app is a single-page client application with thin Next.js API routes. The browser holds all chart state in React; API routes handle CSV persistence and config storage only.

No SSR for chart data. CSV files are fetched client-side, parsed in the browser, and never sent back to the server. The parsed ParsedData object lives only in React state and a Map-based in-memory cache per session.

Data Model

Core Types (lib/types.ts)

ParsedLead

interface ParsedLead {
  leadId:       string;
  fullName:     string;
  assigned:     string;
  createdDate:  Date | null;
  activityDate: Date | null;
  // key = "TagGroup > Tag" label; value = applied/removed timestamps
  tags: Map<string, { applied: Date | null; removed: Date | null }>;
}

ChartConfig

interface ChartConfig {
  id:            string;               // "widget-{timestamp}"
  type?:         WidgetType;
  title:         string;
  query:         ChartQuery;
  color?:        string;               // hex accent color
  colSpan?:      1 | 2 | 3 | 4;         // grid columns (4-col grid = ¼/½/¾/Full)
  chartHeight?:  number;              // px: 200/300/400/500
  seriesColors?: Record<string, string>; // tagLabel → hex (pie/stacked bar)
}

ChartQuery

interface ChartQuery {
  metric:        string | null;  // tag label, "__all__" for all candidates, or null (unset)
  filters:       string[];        // tag labels that must be applied
  criteria?:     CriteriaFilter;  // advanced AND/OR filter (Total widget)
  dateField:     string;          // "created" or a tag label
  groupBy:       GroupBy;         // "week" | "month" | "quarter"
  tagGroupAxis?: string;          // tag group name → X axis shows tags, not time
  excludeRemoved?: boolean;      // only count if tag has no Removed date
  startDate:     Date | null;
  endDate:       Date | null;
  datePreset?:   DatePreset;      // "all_time" | "this_year" | "this_month" | "last_30_days" | "last_90_days" | "custom"
  funnelStages?: string[];        // ordered tag labels (Funnel widget)
}

StoredClient

interface StoredClient {

  blobUrl:     string;       // Vercel Blob private URL (never sent to browser)
  tabs:        ClientTab[];

}

interface ClientTab {
  id:           string;
  name:         string;

}

CSV Format

The app expects a CSV export from a campaign management system (e.g. Zoho Recruit). It auto-detects tag columns by matching column header patterns.

Required columns

Column name (case-insensitive)Field
Candidate ID / Lead IDUnique identifier
Candidate Name / Full NameDisplay name
Assigned ToRecruiter assignment
Created TimeRecord creation date

Tag columns (auto-detected)

Tag columns are identified by these header patterns:

// Applied date columns:
"TagGroup > Tag Applied"
"TagGroup > Tag Applied UTC"
"TagGroup>Tag Applied UTC"   // no spaces around >

// Corresponding removed date columns (same name with "Removed" suffix):
"TagGroup > Tag Removed UTC"

Each matched pair becomes one TagColumn entry. Tags with the same group prefix are automatically grouped into a TagGroup. The group name and tag name are extracted from the header, and a stable label ("TagGroup > Tag") is used as the internal key throughout the app.

Date parsing

The CSV parser handles these date formats:

  • ISO 8601 with time: 2025-06-12T01:26:50Z
  • ISO date-only: 2025-06-12
  • US short with time: 10/6/25 2:22
  • US short date: 10/6/25 or 10/6/2025

MethodDescriptionBodyReturns

blobUrl is never exposed to the browser. The GET /csv route proxies the file from Vercel Blob using the stored private URL. The sanitize() helper strips blobUrl from all client API responses.

Storage

Vercel Blob — CSV files

Each client's CSV is stored as a private blob at clients/{id}/data.csv. When a client is deleted the blob is also deleted. Private blobs require server-side proxying to serve (handled by the /csv API route).

Upstash Redis — client metadata & configs

Client records are stored in Redis (lib/redis.ts). The entire StoredClient object (including all tabs and chart configs) is serialized as a single Redis key per client. Functions exposed: listClients(), saveClient(), getClient(), deleteClient().

Chart config changes are debounced 800 ms before writing to Redis to avoid hammering the database during rapid slider/toggle interactions.

State Management

All app state lives in the useClients() hook (lib/useClients.ts) and is passed down as props. There is no global state manager (no Redux, no Zustand).

StateTypeNotes
clientsStoredClient[]Full client list
activeClientIdstring | nullSelected client
activeTabIdstring | nullSelected tab

hydratedbooleanInitial API load complete
csvLoadingbooleanCSV fetch in progress

CSV caching: A useRef Map keyed by client ID caches parsed ParsedData for the session lifetime. Switching clients re-uses the cache; uploading a new CSV invalidates the cache entry for that client.

Widget System

WidgetShell

WidgetShell is a shared wrapper used by 6 of the 8 widget types. It provides the standard chrome: colored accent strip, drag handle, editable title, gear button (config panel), and remove button.

The gear panel renders in two sections separated by a divider:

  1. configPanel — widget-specific query controls (passed as a prop)
  2. AppearanceControls — color picker, width toggle (¼/½/¾/Full), height toggle (S/M/L/XL)

ChartPanel (bar/line chart) and PieChartWidget do not use WidgetShell — they have their own equivalent header/config implementations with AppearanceControls called directly.

AppearanceControls

Shared component (components/AppearanceControls.tsx) that renders:

  • 12-color palette picker → saves to config.color
  • Width toggle (¼=1, ½=2, ¾=3, Full=4) → saves to config.colSpan (4-column grid)
  • Height toggle (S=200, M=300, L=400, XL=500) → saves to config.chartHeight

SeriesColorPicker

Used by StackedBarWidget and PieChartWidget to assign per-series colors. Each series row is expandable to show the 12-color palette. Colors saved to config.seriesColors as Record<tagLabel, hexColor>.

Time-series stacked bars, one series per tag in the selected group. Per-series color customization.
Pie Chart
'pie'
Donut chart by tag group with legend table. Per-slice color customization.
Table

Ranked table: name, count, share %, inline bar indicator. Sorted descending by count.

Ordered stages. Each stage is a tag label. Shows step-to-step conversion % and overall conversion rate.

Data Processing

All chart data is computed client-side from ParsedLead[] on every render (wrapped in useMemo keyed to the query). No server-side aggregation.

FunctionInputOutput
processChartData leads + query (time-series mode) ChartDataPoint[] — all periods filled, zeros included
processTagGroupChart leads + tagGroupName + query ChartDataPoint[] — one entry per tag in the group
processStackedBarChart leads + stackGroupName + query StackedBarDataPoint[] — dynamic keys per tag label
processFunnelChart leads + funnelStages[] + query FunnelDataPoint[] — count per stage
countLeadsForTotal leads + metric + preset + filters + criteria number

All Candidates mode

Setting query.metric = '__all__' in time-series charts counts all candidates by createdDate (no tag filter). This sentinel value is recognized in processChartData. metric = null (unset) still returns empty data to show the "please configure" empty state.

Interactions

Drag-and-drop reordering

All widgets in a tab use the HTML5 drag-and-drop API (draggable, onDragStart/onDragOver/onDrop/onDragEnd). The dragged widget is shown at 40% opacity; the drop target gets a blue ring. On drop, the chartConfigs array is reordered and saved to Redis.

Title editing

Clicking a widget title in the header activates an inline input. Blur or Enter commits; Escape cancels. The new title is saved immediately via onUpdate(id, { title }).

Config panel

The gear icon toggles a collapsible panel below the widget header. Widget-specific controls are rendered first; the appearance section (color/size) follows, separated by a divider.

Adding a New Widget Type

To add a new widget type to the system:

  1. Add the type string to the WidgetType union in lib/types.ts
  2. Add any new query fields to ChartQuery if needed
  3. Add a data processor function to lib/dataProcessor.ts
  4. Create components/YourWidget.tsx using WidgetShell for the chrome
  5. Add a case 'your_type' to the switch in app/page.tsx
  6. Add a card to the TYPE_META array in components/AddChartModal.tsx
  7. Handle the new type in handleAdd() in AddChartModal.tsx to build the initial ChartQuery
